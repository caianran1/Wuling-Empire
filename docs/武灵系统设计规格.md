### 关于「灵珠种类决定修炼方向」

**这是本次改动里最需要你确认的一点。**

第一部原文只定义了五种**品质**，没有「种类」。但第四部物价写的是  
「极品**僵尸**灵珠」「极品**骷髅**灵珠」「极品**恶魂**灵珠」，  
第二部又说「种类决定修炼方向」——所以灵珠必然还有**来源生物**这一维度。

我的处理：给灵珠物品加了 NBT 字段 `Source`，记录掉落它的怪物 ID。  
尸体生成时写入，搜刮进包后保留，tooltip 上显示。

&#x4F46;**「来源 → 修炼方向」的映射表原文没给**，目前实现是：  
所有来源共享同一份武灵候选表，按你确认的稀有度权重（1/100 vs 1/10）抽取。  
等这份映射表明确了，改 `WuLingType.roll` 一处即可，不用动其他逻辑。

## 二、等级体系

```
木 → 石 → 黄金 → 玄铁 → 钻石 → 下界合金 → 绿宝石
 ↓
每个大境界内部：前期 → 中期 → 后期
```

总索引 = 大境界序号 × 3 + 小境界序号，取值 **0 ~ 20**，共 21 个台阶。

### 小境界晋升（前 → 中 → 后）

无需渡劫、无需物资，纯粹累积修炼进度：

```
每晋升一个小境界所需进度 = thresholdBase × thresholdGrowth ^ 大境界序号
```

默认 `thresholdBase = 120`、`thresholdGrowth = 2.2`：

| 大境界  | 晋升一次所需进度 |
| ---- | -------- |
| 木    | 120      |
| 石    | 264      |
| 黄金   | 581      |
| 玄铁   | 1,278    |
| 钻石   | 2,811    |
| 下界合金 | 6,184    |
| 绿宝石  | 13,606   |

**后期不会自动跨到大境界**——这是原文定的规则，大境界必须走突破流程。

### 修炼动作与进度产出

| 动作   | 默认每次产出  | 适用武灵     |
| ---- | ------- | -------- |
| 造成伤害 | 1 × 伤害值 | 剑、斧、火    |
| 挖掘方块 | 1       | 斧、镐、铲    |
| 弓箭命中 | 6       | 弓        |
| 承受伤害 | 2       | 盔甲、水     |
| 使用道具 | 4       | 水、火、红石、书 |

**关键约束**：只有「真的在使用自己的武灵」才计数。  
剑武灵要求手里拿的是剑（`ItemTags.SWORDS`），镐武灵要求拿镐，  
弓武灵要求拿弓/弩，盔甲武灵要求身上穿着盔甲。水/火/红石/书不限制手持。

## 三、开启、境界上限与修炼速度

### 操作方式

| 操作             | 效果                                   |
| -------------- | ------------------------------------ |
| **Shift + M**  | 凝聚出实体武灵（不需要绑定器，消耗灵力）                 |
| **Shift + N**  | 打开武灵升级面板（不需要绑定器，0.2.20）              |
| **手持灵珠右键村民牧师** | 请牧师开启武灵 —— 种类**由牧师抽取**，玩家不能选（0.2.21） |
| 绑定器 Shift + 右键 | 打开武灵选择界面（选种类并绑定）                     |
| 绑定器 右键         | 打开武灵升级面板（快捷键的等价入口）                   |

**种类由玩家自己选**，不是随机。按下后会弹出 `WuLingChooseScreen`，  
十种武灵两列排开，各自标注原文给的稀有度（稀有 1/100、常见 1/10）作为参考信息。  
选定后客户端把种类 key 发给服务端，服务端校验物资并写入。

> 注意：既然改为自选，原文的 1/100 与 1/10 就不再是「抽取概率」，  
> 只作为稀有度的展示标签保留。如果后续希望稀有种类有额外门槛  
> （例如极品灵珠才能选剑），在 `WuLingBinding` 里加一道校验即可。

本地会先粗校验一次：身上有没有绑定器、有没有灵珠，  
不满足直接给提示，不必弹界面。最终判定仍然在服务端。

Shift + M 与 Shift + N 都走 `ModKeyMappings`（默认 M / N 键，归入「武灵帝国」按键分类）。  
1.20.1 的 `KeyMapping` 不支持修饰键，所以两个键都由按键映射注册，  
Shift 在 `ClientTickHandler` 里用 `InputConstants.isKeyDown` 额外判断——  
只按 M 提示「凝聚武灵需要按住 Shift」，只按 N 提示「打开武灵面板需要按住 Shift」，都不会误触发。

两个快捷键都**不需要携带武灵绑定器**（0.2.14 起凝聚、0.2.20 起开面板）。  
面板本身是纯客户端界面，数据由服务端的 `WuLingSyncPacket` 推送，因此打开时无需发包。

#### 凝聚（Shift + M）的 0.2.14 口径

| 项       | 口径                                              |
| ------- | ----------------------------------------------- |
| 是否需要绑定器 | **不需要**（绑定器只管开武灵 / 选种类 / 开面板）                   |
| 是否消耗灵珠  | 不需要                                             |
| 是否消耗灵力  | **需要**，一次 `condenseSpiritCost`（默认 25，百分制）；不足则拒绝 |
| 例外      | 创造绑定器绑定后自动送的那一次**免费**                           |

绑定（选种类）仍然需要背包里有绑定器 + 至少一颗灵珠，  
灵珠取用顺序：副手 → 主手 → 背包自上而下。

### 村民牧师：抽取开启武灵（0.2.21）

> 原文口径：「给村民牧师加入武灵开启的技能（是抽取而不是选择）」

| 项      | 口径                                                                              |
| ------ | ------------------------------------------------------------------------------- |
| 触发     | **手持灵珠右键村民牧师**（空手右键仍是原版交易）                                                      |
| 与交易的关系 | 只要手里拿着灵珠，这次右键就被牧师接管，不会弹出交易界面；没拿灵珠完全不干涉                                          |
| 谁能开    | 只有职业 = `minecraft:cleric`（牧师）的村民；其它职业无效                                         |
| 种类     | **抽取**，走 `WuLingType.roll`：剑 / 弓 / 水 / 火 / 书 各 1 份权重，斧 / 镐 / 铲 / 红石 / 盔甲 各 10 份 |
| 修炼速度   | 由**你交出去的那颗灵珠**品质决定（凡品 ×1 → 极品 ×3），见下方表格；**上限与品质无关**                             |
| 消耗     | 手里那叠灵珠扣 `bindingBeadCount`（默认 1 颗）；不需要武灵绑定器                                     |
| 重复开启   | 已拥有武灵时拒绝（牧师摇头 + 冒火），要换先 `/wuling spirit unbind`                                 |
| 表现     | 附魔台音效 + 牧师「嗯哼」+ 玩家升级音 + `ENCHANT` 符文粒子 + 绿色村民粒子                                 |

**这就是生存玩家开启武灵的正路**：绑定器是「仅限创造模式取得」的物品（原文设定），  
所以生存里只能请牧师抽签；想自己挑种类只能开创造拿绑定器。

代码入口：`ModEvents#onClericOpenWuLing`（判定职业、决定是否吞掉原版交互）  
→ `WuLingBinding#openByNpc`（真正的绑定与消耗）。

### 品质 → 修炼速度（0.2.22 口径）

> 用户原话：「品质上限不由你交出去的那颗灵珠决定，所有都一样的上限，  
> 只是修炼的速度加成不一样」

| 项    | 口径                                                                      |
| ---- | ----------------------------------------------------------------------- |
| 境界上限 | **人人相同**，一律到 `Config.maxRealm`（默认 6 = 绿宝石·后期）。凡品灵珠开出来的武灵照样能修到绿宝石        |
| 灵珠品质 | **只决定修炼速度倍率**，即每次修炼动作累积的进度乘几倍                                           |
| 触发处  | `WuLingData#addProgress` 里 `progress += amount * cultivationBonus`，一处收口 |
| 表现   | 灵珠 tooltip 多一行「修炼速度 ×N」；升级面板显示「修炼速度 ×N（上限人人相同）」                         |
| 创造成本 | 创造绑定器不消耗灵珠 → 无品质加成，按 ×1 开启                                              |

| 灵珠品质 | 修炼速度加成（`cultivationBonus*`） | 攒满同一档进度的相对耗时 |
| ---- | --------------------------- | ------------ |
| 凡品   | ×1.0（基准）                    | 1.00         |
| 良品   | ×1.25                       | 0.80         |
| 优品   | ×1.5                        | 0.67         |
| 上品   | ×2.0                        | 0.50         |
| 极品   | ×3.0                        | 0.33         |

倍率可在 `Config.cultivationBonusFan ~ cultivationBonusJi` 里调。  
（2026-09-27 之前的旧存档没有这个字段，读入时按 ×1.0 处理 —— 想拿加成可以重开一次武灵。）

> 注：配置键从旧的 `capFan ~ capJi` 换成了 `maxRealm` + `cultivationBonus*`。  
> 老配置文件里的旧键仍然存在但**不再被读取**，这是故意的 ——  
> Forge 不会把已生成的配置跟随代码默认值更新，沿用旧键名会出现「改了却没生效」的假象。

## 四、大境界突破流程

```
已开启武灵，且处于当前大境界的「后期」
        │
        ├─ 未达后期      → 提示「需先修炼到后期」
        ├─ 触及统一上限  → 提示上限境界（人人相同），拒绝
        ├─ 物资不足      → 提示「物资不足」
        ▼
  扣除全部物资 → 境界 +1（小境界归零）→ 推送新数据
```

> **突破与灵力完全无关**（0.2.15 起）：  
> 既不消耗灵力，也不要求灵力圆满（旧的「灵力满 100% 才能突破」门槛已删除）。  
> 灵力只与「凝聚武灵」挂钩 —— `condenseSpiritCost` 默认 25（百分制），不足则无法凝聚。  
> `breakthroughConsumesSpirit` 默认 `false`；配置键由旧的 `breakthroughClearsSpirit` 改名而来，  
> 免得老配置文件里的 `true` 继续生效。

### 凝聚出的武灵比原版强多少（0.2.14 起；0.2.26 改为「每档碾压上一档」）

`WuLingType#empower` 会在凝聚时给物品**额外挂一条属性修饰符**（写在物品 NBT 上，  
原版换装备时会自动重新计算，见 `LivingEntity#handleEquipmentChanges`）：

**最终数值 = 该物品原版同款的数值 × 境界倍数**（配置默认 100% 时）

实现上挂出去的修饰符 = 原版数值 × (境界倍数 − 1) × 配置百分比。  
（攻击力另加玩家自身的基础攻击力 1 一起算，因为原版 tooltip 上的「木剑 4」= 修正值 3 + 这 1 点。）

| 配置项                   | 默认  | 效果                                    |
| --------------------- | --- | ------------------------------------- |
| `manifestAttackBonus` | 100 | 剑/斧/镐/铲：按原版攻击力百分比追加，再乘 (境界倍数 − 1)     |
| `manifestArmorBonus`  | 100 | 盔甲：按原版护甲值 / 韧性百分比追加，再乘 (境界倍数 − 1)     |

**境界倍数**（`WuLingRealm#manifestMultiplier`）

| 境界   | 倍数     | 剑：原版 → 凝聚物      | 相邻倍率   |
| ---- | ------ | --------------- | ------ |
| 木    | 3      | 4 → **12**      | —      |
| 石    | 4      | 5 → **20**      | 1.67×  |
| 黄金   | 8      | 4 → **32**      | 1.60×  |
| 玄铁   | 9      | 6 → **54**      | 1.69×  |
| 钻石   | 11     | 7 → **77**      | 1.43×  |
| 下界合金 | 14     | 8 → **112**     | 1.45×  |
| 绿宝石  | **15** | 16 → **240**    | 2.14×  |

**每一档都严格碾压上一档（≥1.43 倍），没有任何一档在原地踏步。**

- **为什么倍数不是等比的（黄金 8 > 石 4，玄铁 9 却只比黄金多 1）**：  
  原版各材质的底子**不是等差**的——剑的伤害是 木 4、石 5、**金 4（比石剑还低）**、  
  玄铁 6、钻石 7、下界合金 8，绿宝石是单独设计的物品 16。要让**实际数值**成阶梯，  
  倍数就得按底子补偿：黄金档必须给到 8，否则会出现「黄金境界不如石境界」的倒挂。  
  （金甲的原版韧性为 0，所以黄金档只有护甲值加成，没有韧性加成。）
- **工具类的挖掘速度**：原版没有「挖掘速度」属性/修饰符，只有 `Tier#getSpeed`，  
  所以 0.2.25 起斧 / 镐 / 铲按境界附赠**效率附魔** `min(境界序号+1, 5)`  
  （木 效率 I → 钻石及以上 效率 V），让低境界工具在挖掘上也强于原版同款。
- 绿宝石境界各件凝聚物的实际表现（配置默认 100%，倍数 15）：
  | 种类 | 基础（含材质伤害档）      | 武灵之力追加 | 附魔      | 合计                       |
  | -- | --------------- | ------ | ------- | ------------------------ |
  | 剑  | 16              | +224   | 锋利 V +3 | **243**                  |
  | 斧  | 18              | +252   | —       | **270**                  |
  | 镐  | 14              | +196   | —       | **210**                  |
  | 铲  | 14.5            | +203   | —       | **217.5**                |
  | 胸甲 | 护甲 16 / 韧性 12   | 护甲 +224 / 韧性 +168 | — | 护甲 **240** / 韧性 **180** |
  对比：钻石境界的钻石剑 **77**、下界合金境界 **112** ——  
  绿宝石剑（243 含附魔）是钻石境界的 **3.2 倍**、下界合金境界的 **2.2 倍**、  
  原版钻石剑（7）的 **35 倍**，一击即可秒杀满血末影龙（200 血）。
- 没有对应属性的（弓、水/火/红石/书）自然跳过；弓的强化仍靠随境界加的**力量附魔**。
- 物品 tooltip 里会多一行「武灵之力：攻击力额外 +N」，方便核对。

> 想把整体强度压回来：`manifestAttackBonus` / `manifestArmorBonus` 各改小即可  
> （倍数是代码常量、配置是全局乘数）。要让某一件单独更强，在 `WuLingType#manifest`  
> 里加一条分支，单独传一个倍数给 `empower`。

### 绿宝石境界的装备：整套单独设计（0.2.16，数值 0.2.17 大幅上调）

### 分批缴纳（背包放不下）

后期突破要十几二十组物资，背包根本装不下，所以物资存在**两个去处**：

| 去处                                  | 说明                |
| ----------------------------------- | ----------------- |
| 背包                                  | 尚未缴纳的物资           |
| **缴纳池**（`WuLingData` 的 `Submit` 标签） | 已缴入的物资，可分批攒，与背包无关 |

- 面板按钮 **「提交物资」**（`WuLingSubmitPacket`）：把背包里**当前这档还缺的**物资尽量缴进池子  
  （只缴到需求上限，不多吞），背包腾空一块就能再缴一次，可以反复多次。
- 面板按钮 **「突破」**：**先自动把背包里剩余的也缴进池子**，再判定池子是否齐全。  
  所以一次性带齐时，点一次突破即可，不必先手动提交。
- 每一行显示 `已凑到 / 需要`，行名后追加灰色「已缴 N」，方便看清缴了多少。
- 缴纳池按**目标大境界**记账（`SubmitTarget`）；目标变了（已突破 / 改了配置）会  
  **自动原物退还**给玩家，不会凭空吞掉。`/wuling spirit unbind` 也会先退还再解绑。

### 物资需求配置

格式 `"物品注册名;数量"`，另有两个特殊键代表「每种怪物的灵珠各 N 个」：

| 特殊键              | 含义                        |
| ---------------- | ------------------------- |
| `ALL_BEADS;N`    | **不限品质**，该来源的凡品 ~ 极品灵珠都算数 |
| `ALL_JI_BEADS;N` | 只收**极品**灵珠（旧口径，代码保留兼容）    |


覆盖的怪物集合 = 注册表里全部 MONSTER 分类实体（模组怪物自动纳入）
∪ 本模组出图的怪物（疣猪兽是 CREATURE 分类却照样掉灵珠，靠出图表补进来）
− `Config.NEVER_DROPS`（蠹虫/恼鬼/末影螨）− `Config.EXCLUDED_MOBS` − `Config.BREAKTHROUGH_EXCLUDED_MOBS`。
`BREAKTHROUGH_EXCLUDED_MOBS` 默认排除 **巨人 / 疣猪兽 / 幻术师 / 远古守卫者 / 流浪者 / 监守者**
（它们照样掉灵珠，只是不参与这几档突破的收集要求）。

> **缴纳池的灵珠键带品质段**（`bead|<来源>|<品质>`）：不限品质时一次可能缴进多种品质，
> 分品质记账才能保证退还时「缴的是凡品就退凡品」，不会被白嫖成极品。
> 旧存档里没有品质段的键按极品处理。

| 石 → 黄金 | 圆石 ×512 + 煤 ×64（占位） |

#### ⚠️ 绿宝石档的键名换过一次（0.2.23）

0.2.13 就把绿宝石档的默认值从 `ALL_JI_BEADS;10`（只收极品）改成了 `ALL_BEADS;10`（不限品质），
**但配置键名 `netherite_to_emerald` 没换** —— 而 Forge 的配置文件一旦生成就固定在那里，

另外启动时会把六段突破的**生效值**打进日志（`Config#logEffectiveRequirements`），
以后遇到「改了却没生效」直接看日志即可，不用进游戏试。

## 五、怪物等级（武灵属性，0.2.21）

> 原文口径：「加入怪物等级系统（用木 → 石 → 黄金 → 玄铁 → 钻石 → 下界合金 → 绿宝石），
> 攻击都用本属性的剑做攻击；每种怪物都有小概率有属性，但怪物的等级越高越非常稀有！」

### 规则

| 项 | 口径 |
|---|---|
| 谁能有等级 | **敌对生物**（`Enemy`）且不在排除名单里；和平生物与村民不参与 |
| 等级阶梯 | 与玩家武灵**同一套 7 大境界**：木 → 石 → 黄金 → 玄铁 → 钻石 → 下界合金 → 绿宝石 |
| 有等级的概率 | `monsterTier.tierChance`，默认 **10%**（调 0 即关闭整个系统） |
| 等级分布 | 权重 = 1 ÷ `tierRarityRatio` ^ 阶数，默认 2.5 → 等级越高越非常稀有 |
| 武器 | **本属性的剑**：木剑 / 石剑 / 金剑 / 铁剑 / 钻石剑 / 下界合金剑 / **绿宝石剑**（本模组单独设计的那把） |
| 伤害 | 剑自带的属性修饰符由原版 `LivingEntity#handleEquipmentChanges` 自动挂上，不必自己写伤害逻辑 |
| 血量 | 倍率 = 1 + 大境界序号 × `tierHealthBonusPerRealm`（默认 0.5） |
| 掉落 | 主手物品掉落率钉成 **0**（否则刷出一柄绿宝石剑就等于绕开整条晋升线） |
| 提示 | 打死带等级的怪时，给击杀者报一句「击杀了一头 钻石阶 妖兽」 |

### 实际概率（默认 10% / 2.5）

| 等级 | 在「有等级的怪」里 | 占全部怪物 |
|---|---|---|
| 木 | 60.1% | 6.0% |
| 石 | 24.0% | 2.4% |
| 黄金 | 9.6% | 0.96% |
| 玄铁 | 3.8% | 0.38% |
| 钻石 | 1.5% | 0.15% |
| 下界合金 | 0.61% | 0.061% |
| 绿宝石 | 0.25% | **约 1/4000 只怪** |

### 排除名单（`monsterTier.tierExcludedMobs`）

- 不近战的：苦力怕、史莱姆、岩浆怪、恶魂、烈焰人、女巫、潜影贝；
- 不渲染手持物 / 另有攻击方式的：幻翼、守卫者、远古守卫者、蠹虫、末影螨、凋灵、末影龙。

理由：给它们剑既不会用也看不见，白掷一次骰子。删掉某项即可让它们参与。

### 几个取舍

- **武器即等级**：不做名字前缀、不加额外 UI。木阶一柄木剑、绿宝石阶一柄绿剑，
  一眼可辨，也顺便解释了「为什么这只僵尸打得这么疼」。
- **不设自定义名字**：给怪物 `setCustomName` 会牵扯「带名怪不消失」的判定，得不偿失。
- **血量走固定 UUID 的属性修饰符**，每次进世界先摘后挂，区块反复加载不会叠血；
  补血只在第一次应用时做，重载不会白送一次满血。
- **等级只掷一次**：结果写进怪物的 Forge 持久化数据（`ForgeData`），区块卸载再加载不会重掷。
- **隐性联动**：灵珠品质本来就按「来源怪最大生命值」推算（`CorpseEntity#randomQuality`），
  所以高阶怪掉的灵珠品质天然更好。

代码入口：`ModEvents#onEntityJoinLevel` → `MonsterTier#onJoin`（`wuling/MonsterTier.java`）。

## 九、Forge 版本兼容性（0.2.24）

### 结论

产物可加载到 **Minecraft 1.20.1 的全部 132 个 Forge 版本**上：`47.0.0` ~ `47.4.23`
（官方推荐版是 47.4.10，最新版 47.4.23）。

`mods.toml` 里声明的范围：

| 项 | 值 | 含义 |
|---|---|---|
| `loaderVersion` | `[47,)` | 47.x 全部 |
| forge 依赖 `versionRange` | `[47,)` | 同上 |
| minecraft 依赖 `versionRange` | `[1.20.1,1.21)` | 1.20.1 |

### 做法：编译目标锁在「最低」版本

`gradle.properties` 的 `forge_version` 故意设成 **47.0.0**（不是最新的 47.4.23）。

用最低版本编译，产物字节码里就**只会引用 47.0.0 时已经存在的 API**，
于是天然能跑在更高的版本上；反过来编译最新版则很容易悄悄用上后期新增的 API，
在老版本上直接崩。代价是开发时 `runClient` 跑的是 47.0.0。

> 想在**新版** Forge 上调试：把 `gradle.properties` 的 `forge_version` 改回 `47.4.23`，
> 或者临时用 `gradle runClient -Pforge_version=47.4.23`（命令行属性优先，不用改文件）。

### 踩到的三个坑

**① 主类构造函数必须是无参的**（影响最大）

- `47.0.0 ~ 47.3.7` 的 `FMLModContainer#constructMod()` 只有一句
  `modClass.getDeclaredConstructor().newInstance()` —— **只认无参构造函数**，
  找不到就 `ModLoadingException` 加载失败。
- `47.3.10` 起才支持把 `FMLJavaModLoadingContext` 注入构造函数
  （实现是「先试带参、`NoSuchMethodException` 再退回无参」）。
- 所以**写无参构造函数在新老版本都能被实例化**，是最安全的写法。
  本项目原来用的是 `public WulingEmpire(FMLJavaModLoadingContext context)`，
  在 **132 个版本里的 89 个**（47.0.x 23 个 + 47.1.x 38 个 + 47.2.x 20 个 + 47.3.0~47.3.7 8 个）上会加载失败。

**② 配置注册用 `ModLoadingContext`**

`FMLJavaModLoadingContext#registerConfig` 不能直接用：47.0.0 里
`FMLJavaModLoadingContext` 是个**独立类**（不继承 `ModLoadingContext`），根本没有这个方法；
继承关系是后期才加的。改用从 1.20.1 初版就存在的
`ModLoadingContext.get().registerConfig(ModConfig.Type.COMMON, Config.SPEC)` 即可。

**③ `ResourceLocation` 的静态工厂是后期 backport 进来的**

`fromNamespaceAndPath` / `parse` / `withDefaultNamespace` / `bySeparator` / `tryBySeparator`
这一批**是 Forge 在 1.20.1 后期补进 MC 的**，47.0.0 里没有。
统一改用两参构造函数 `new ResourceLocation(namespace, path)` —— 它从 1.20.1 初版就在，
在最新版也照样可用（只是有 deprecation 提示）。

原来项目里有 4 处用了 `fromNamespaceAndPath`：

| 文件 | 位置 |
|---|---|
| `WulingEmpire` | `id(String)` |
| `capability/ModCapabilities` | `SPIRIT_POWER_ID` / `WU_LING_ID` 两个**静态字段** |
| `item/SpiritQuality` | `itemTexture()` |
| `wuling/WuLingType` | `id()` |

## 十、产物命名（0.2.27）

构建产物统一命名：

```
Wuling-Empire-v<mod_version>.jar
    └─ 例：Wuling-Empire-v0.2.27.jar
```

实现（`build.gradle`）：

```groovy
version = "v${mod_version}"     // → v0.2.27
base {
    archivesName = 'Wuling-Empire'
}
```

- 只用 `archivesName` + `version` 两处，`jar` / `reobfJar` / `sourcesJar`
  都从 `base` 派生，因此**不会产生两份名字不同的产物**。
- `version` 带 `v` 前缀只影响文件名；`mods.toml` 里的 `version="${mod_version}"`
  取自 `gradle.properties`，仍是干净的 `0.2.27`。
- Manifest 的 `Implementation-Version` 也显式写回 `mod_version`（不带 `v`），
  防止解析 Manifest 的工具把 `v0.2.27` 当非法版本号。
- **与文件命名无关、不要动的东西**：`mod_id=wulingdiguo`（存档、注册表 ID、
  配置目录 `config/wulingdiguo-common.toml` 都靠它）、`displayName`（游戏 Mod 列表显示）。

> 历史：≤ 0.2.26 的产物名为 `wulingdiguo-0.2.x.jar`（当时 `archivesName = mod_id`）。

### 附一：Mod 名称的中文乱码（0.2.27 修复）

**症状**：游戏 Mod 列表里显示成 `WuLing Diguo / æ¦çµå¸å½`、简介也是一串西欧字母。
**存在时间**：至少 0.2.20 ~ 0.2.26 的产物全部中招（不是新引入的问题）。

**排查链**（三步，值得记下来）：

1. **看 jar 里的字节**，不要看构建日志：
   `META-INF/mods.toml` 的 `displayName` 是
   `c3 a6 c2 ad c2 a6 …` —— 这是「UTF-8 的中文被按 latin-1 解码后再编成 UTF-8」的
   典型**双重编码**指纹（正常应是 `e6 ad a6 e7 81 b5 …`）。
2. **确认读的一方没问题**：Forge 1.20.1 用 NightConfig 读 mods.toml。
   反编译 `com/electronwill/nightconfig/core/file/GenericBuilder.class` 可见
   `getstatic StandardCharsets.UTF_8` → **默认就是 UTF-8**，不必怀疑 Forge。
3. **问题在写的一方**：Gradle 按 **ISO-8859-1** 读取 `gradle.properties`
   （沿用 `java.util.Properties` 规范），所以 `mod_name=武灵帝国` 一进 Gradle 就已
   变成 `æ¦çµå¸å½`；再经 `processResources` 的 expand 以 UTF-8 写盘 → 双重编码。

**改法（两处）**：

| 位置 | 改动 |
|---|---|
| `gradle.properties` | `mod_name` / `mod_description` 的非 ASCII 全部写成 `\uXXXX` 转义 |
| `build.gradle` | `tasks.named('processResources') { filteringCharset = 'UTF-8' }` |

第二处是**必要的加固**：不显式指定时，expand 的写盘字符集取「构建机默认字符集」，
在中文 Windows（GBK）上构建会把中文写成 GBK 字节，依旧乱码 —— 也就是说，
原来的构建能侥幸不出第二种错，只是因为构建命令带了 `-Dfile.encoding=UTF-8`。

**规则**：`gradle.properties` 视为**纯 ASCII 文件**。要在里面写非 ASCII 值？
先转义。文件顶部已加了醒目注释。

**验收**：解包 jar，`mods.toml` 里 `武灵帝国` 必须是 `e6 ad a6 e7 81 b5 e5 b8 9d e5 9b bd`。

### 附二：另两处「名字」

- `settings.gradle` 加了 `rootProject.name = 'Wuling-Empire'`：
  Manifest 的 `Implementation-Title` 取自它，不写就取文件夹名（改文件夹名＝改产物元数据）。
- Manifest 的 `Implementation-Version` 显式写 `mod_version`（`0.2.27`），
  不跟着文件名一起带 `v` 前缀，方便校验工具解析。

### 为什么 `build/` 不在仓库里

`.gitignore` 第 3 行就是 `build/`，`git check-ignore -v build` 可直接验证：

```
.gitignore:3:build/     build
```

这是**正确行为**，不是上传失败：

> 但单次 ≤100 个文件、单文件 ≤25 MB —— `build/` 有 214 个文件，同样过不去。

### 发布工具 `tools/publish_github.py`

WorkBuddy 沙箱注入了本地 HTTP 代理，`git push` 会被拒绝
（`CONNECT tunnel failed, response 502`），绕开代理直连又被沙箱屏蔽，
因此本项目**改用 GitHub REST API 同步**（`api.github.com` 与 `uploads.github.com` 均放行）。

```bash
python tools/publish_github.py status            # 列出本地与远程的差异
python tools/publish_github.py sync              # 提交并推送到 main
python tools/publish_github.py sync -m "说明"    # 自定义提交信息
python tools/publish_github.py release 0.2.29    # 建 tag + Release + 上传 jar
python tools/publish_github.py sync --release    # 同步源码后再发布
```

实现要点：

- **差异用 blob sha 对撞**：远程 `git/trees?recursive=1` 的 sha 对本地
  `git hash-object -w --path=<p> <p>`。`--path` 让 `core.autocrlf` 与 `.gitattributes` 生效，
  所以算出的 sha 与 GitHub 完全可比 —— **既精确又不会出现 CRLF 假差异**。
- **上传内容从 `git cat-file blob` 取**，与 sha 严格对应；提交后还会校验远程返回的 sha 是否一致。
- **文件枚举交给 git**（`ls-files -s` + `ls-files --others --exclude-standard`），
  所以 `.gitignore` 天然生效，无需自己实现忽略逻辑。
- **二进制安全**：blob 以 base64 提交，jar / png 不会被破坏
  （MCP 的 `push_files` 是纯文本接口，传二进制会静默损坏，不可用于此场景）。

|---|---|
| tag | `v0.2.28` |

| 页面 | https://github.com/caianran1/Wuling-Empire/releases/tag/v0.2.28 |

## 十三、产物命名与测试版后缀（0.3.0 起）

### 命名规则

| 场景 | 文件名 |
|---|---|
| 正式版（`mod_suffix` 留空） | `Wuling-Empire-v<mod_version>.jar` |
| 测试版（`mod_suffix=test`） | `Wuling-Empire-v<mod_version>-test.jar` |

```
Wuling-Empire-v0.3.0.jar          ← 正式版
Wuling-Empire-v0.3.0-test.jar     ← 测试版
```

实现（`build.gradle`，紧跟在 `plugins {}` 之后）：

```groovy
def modSuffix = (findProperty('mod_suffix') ?: '').toString().trim()
version = "v${mod_version}" + (modSuffix ? "-${modSuffix}" : '')
base { archivesName = 'Wuling-Empire' }
```

`mod_suffix` 定义在 `gradle.properties`（默认留空）。三种写法都行：

| 方式 | 例子 | 适用 |
|---|---|---|
| 改文件 | `mod_suffix=test` | 整段时间都发测试版 |
| 命令行 | `gradle build -Pmod_suffix=test` | 只这一次，不动文件 |
| 留空 | `mod_suffix=` | 正式版 |

后缀词任意，只要**纯 ASCII、不带空格和点**（`test` / `pre1` / `rc1` / `dev` 都可以）。
不要写成 `0.3.0-test.1` 之类带点的值，语义化版本比较会出问题。

### 后缀「只」影响文件名

| 字段 | 是否受影响 |
|---|---|
| jar 文件名 | ✅ 加后缀 |
| Manifest `Implementation-Version` | ✅ 加后缀（`0.3.0-test`），便于区分两类产物 |
| `mods.toml` 的 `version` | ❌ 仍是 `${mod_version}` = `0.3.0`（Forge 靠它判版本，必须干净） |
| `mod_id` / `displayName` | ❌ 不动 |

> 为什么 `mods.toml` 的 version 不带后缀：Forge 用语义化版本比较 mod 依赖关系，
> 而 `-test` 是 semver 的**预发布标识**，会让「0.3.0-test < 0.3.0」成立 ——
> 万一写成依赖坐标，正式版反而被判为更新。文件名带后缀足够区分了。

### 发布

```bash
# 正式版
python tools/publish_github.py release 0.3.0
#   产物 build/libs/Wuling-Empire-v0.3.0.jar  → tag v0.3.0

# 测试版
python tools/publish_github.py release 0.3.1-test
#   产物 build/libs/Wuling-Empire-v0.3.1-test.jar → tag v0.3.1-test
```

`publish_github.py` 的产物路径就是按 `Wuling-Empire-<tag>.jar` 拼的，
所以**带后缀直接跟着 tag 走**，无需额外参数。要用别的文件名（比如改名过的 jar）
再加 `--jar <路径>`。

|---|---|---|

### 上传资产的 502 重试（0.3.0 加固）

发布 v0.3.0 时 `uploads.github.com` 连续 3 次报
`Tunnel connection failed: 502 Bad Gateway`，而 `api.github.com` 全程正常 ——
沙箱代理对该主机的拦截是**间歇性**的（同一时刻 `uploads.github.com/user` 能通、根路径不通）。

`publish_github.py` 因此做了两层加固：

| 层 | 做法 |
|---|---|
| 请求重试 | 网络层异常 / HTTP 5xx / 429 自动重试，最多 4 次，退避 2s / 4s / 6s；4xx（除 429）是确定性错误，立即返回 |
| 上传双通道 | `uploads.github.com` 失败时自动切到 `api.github.com/repos/{owner}/{repo}/releases/{id}/assets?name=...` |

补充观测：两个主机解析到不同 IP（`uploads.github.com` → `20.205.243.161`、
`api.github.com` → `20.205.243.168`），代理对两个后端的放行策略可能不一致，
所以**不要把「上传成功」当必然**，脚本的自动重试是必需的。
